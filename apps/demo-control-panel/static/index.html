The persona and situation

You are the on-call SRE for a retail bank's digital channels. Customers make payment transfers in the web banking app. The bank needs to know when transfers slow down or fail, why, and who needs to act, before customers start complaining.

During the demo you break the payment path on purpose (a bad release, a slow database, errors, added latency) and use Elastic to go from alert to root cause, check the SLO, and onboard a new service without any Kibana setup.

The customer's view: open the web banking app ↗. Check a balance or send a transfer while a fault is on to see what customers experience; each action shows its trace.id, which you can paste into Kibana.

How the app works

A small payments application runs in the banking namespace on Amazon EKS. A transfer follows this path:

  1. The customer uses the bank UI in their browser to check a balance or send a transfer.
  2. web-banking (Node.js) serves that page and receives the customer's transfer request.
  3. transfer-service (Java, Spring Boot) orchestrates the transfer.
  4. fraud-check (.NET) scores the transfer for fraud.
  5. accounts-ledger (Python, FastAPI) posts the debit and credit to Postgres.

A k6 load generator in the cluster sends steady traffic straight to web-banking's API, so the charts have data without anyone clicking. fx-rates (Python) is the "new service" that you onboard live. The faults are driven by a fault-config ConfigMap, which the services re-read every 5 seconds. The Trigger errors tab edits that ConfigMap for you.

How it is instrumented

  • No backend service contains an OpenTelemetry SDK. Each deployment has one pod annotation, and the OpenTelemetry Operator injects the matching language auto-instrumentation (Java, Node.js, .NET, Python) when the pod starts.
  • The bank UI is the exception: the OpenTelemetry browser SDK (real user monitoring) records page loads and each customer action as web-banking-frontend. It adds a trace header to each API call, so every backend trace starts with the customer's click.
  • The auto-instrumentation produces traces, metrics and logs for every request, with the service name, version and environment set as resource attributes.
  • The Elastic Distribution of OpenTelemetry (EDOT) collectors, installed with the opentelemetry-kube-stack Helm chart, add the infrastructure view. A DaemonSet collects node, pod and container metrics and logs. A cluster collector collects Kubernetes cluster metrics and Postgres metrics.

How the signals get to Elastic Cloud

  1. Services send OTLP to the EDOT DaemonSet collector on their node, which adds Kubernetes metadata (pod, namespace, deployment). The browser sends its spans to web-banking on the same address as the page, and web-banking passes them on to that collector, so no collector is exposed to the internet.
  2. The DaemonSet and cluster collectors forward everything over OTLP to an EDOT gateway collector in the cluster.
  3. The gateway derives APM metrics from the traces and writes the data to Elasticsearch on Elastic Cloud Hosted 9.5, authenticating with an API key. The data is stored in the OpenTelemetry-native format, with no translation to a proprietary schema.
  4. In Kibana, Terraform has already created the SLO, alert rules, ML anomaly job, dashboards and users. Any new service that sends data is picked up by them automatically.
